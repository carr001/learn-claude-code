s15 → s16 演进图解

从"多种机制，一个循环" 到"模型决定单步，脚本决定编排"

s01 → … → s14 → s15 → s16 → s17

🎯 一句话理清两者

s15 · 集成宿主

"多种机制，一个循环"
  • 26 个工具挂在同一个 while True
  • 每一轮都由模型现场决定下次调什么工具
  • 步骤记录在 messages[]，压缩就丢
  • hooks / 权限 / 记忆 / 团队 / 后台 / cron / MCP 全部就位
  • 能处理探索性任务（下一步依赖上一步发现）
➜

s16 · Workflow Runtime

"一次 tool_use，跑完一整套编排"
  • 新增一个 Workflow 工具，其他 25 个不变
  • 把固定流程写死在脚本里，模型只填参数
  • 进度写到 journal.jsonl，磁盘持久化
  • 新增 parallel / pipeline / phase 并行原语
  • 专治重复性任务（步骤已知、需并行、跑得贵）
关键洞察： s16 不是替换 s15。它是在 s15 之上加了一层编排—— 主循环还是那个 while True，Workflow 只是工具池里多出来的一个工具。 但这一个工具，把 agent 系统从"聊天工具"升级为"业务自动化引擎"。

✅ schema 校验 → 强制结构化输出

每个子 agent 只能返回符合 schema 的 JSON。不符合？自动重试一次。

"我发现了 3 个安全问题:1. SQL 注入... 2. 弱密码..."   # 🤯 谁来解析?

# s16:强制 JSON schema
await ctx.agent(prompt, schema=FINDINGS_SCHEMA, label="audit:安全")
# 返回:{"findings": [{"title": ..., "severity": "high"}, ...]}
# 下游代码直接 for f in result["findings"]: 遍历,不用解析自然语言

🔑 s16 的 6 大关键机制

🎫
Workflow 工具
模型只提供 name + args + resume_from_run_id， 不能提交可执行代码。宿主 registry 只暴露白名单 workflow。
🎼
编排原语
agent() / parallel() / pipeline() / phase() / log() —— 只暴露少量能力，脚本不能读文件/跑 shell。
📋
JSON Schema 强校验
子 agent 输出必须匹配 schema。不匹配 → 自动重试一次 → 还不行就抛错。 把不确定性挡在编排层外。
📓
Journal 磁盘账本
每次 agent() 完成立即追加到 .runtime/{runId}.journal.jsonl， flush 落盘，保证断电也不丢。
🔑
稳定内容哈希 key
用 hash(kind + label + prompt + schema) 作 key， 不用计数器——因为 parallel/pipeline 完成顺序不定， 计数器两次跑会错位。
📡
SDK 风格事件流
task_started → task_progress* → task_notification。带 agent 数和 token 数， 方便进度条 / 观测 / 计费。

📊 s15 vs s16 · 完整对照

维度 s15 Agent Harness 集成 s16 Workflow Runtime
主循环 单个、模型驱动 主循环不变；工具背后执行脚本编排
谁决定下一步 模型逐轮决定 脚本预先写好编排流程
多 agent s06 子 agent，一次性派 agent-runner 边界执行可续跑的调用
tool_use 次数 20+ 轮（每步一次） 1 次（一次调用跑完全流程）
并行能力 ❌ 无（一轮只能一个 tool_use） ✅ parallel + pipeline
输出结构 模型自由发挥 schema 强制校验 + 一次重试
中间结果 塞 messages 污染上下文 存变量里，不进对话历史
中断恢复 ❌ 从头再来 ✅ runId + journal 缓存续跑
适合场景 探索性任务（下一步依赖上一步发现） 重复性固定流程（代码审查、批量翻译、多维分析）

💡 分层哲学的深化

"s06 的子 agent 是模型临场派一次；
s16 把编排写成可续跑的宿主代码。"
— s16 README
🧠 LLM 层 · 语义决策（选哪个 workflow / 填什么参数）
🎼 编排层（s16 新增） · 并发调度 / journal / schema 校验
🛠 Harness 层（s15） · 工具 / hooks / 权限 / 记忆 / 团队 / 后台 / cron

s15 让 harness 承担基础执行确定性；
s16 让 harness 承担编排级确定性—— 把"用什么顺序、并发多少、怎么恢复"这些原本靠模型直觉的决策，
下沉到脚本代码。

🤔 什么时候用 s16？什么时候别用？

✅ 用 s16 workflow

  • 📋 重复性任务：代码审查、批量翻译、批量数据分析
  • 🗺 流程已知：步骤和依赖执行前就确定
  • 🔀 可并行：多维度/多文件独立处理
  • 💸 跑得贵：token 消耗大，重跑代价高

❌ 别用 s16 workflow

  • 🔍 探索性任务：调 bug（每步依赖发现）
  • ⚡ 单次任务："帮我写个函数" 一次调用够了
  • 🎲 动态决策多：需要 LLM 每步都判断分支
  • 📏 短流程：只有 1-2 步，编排开销大于收益
